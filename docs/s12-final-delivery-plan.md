## 二、S21 桌面遗留：最终演示前预检

S21 报告中的 A/B/C GUI 项均未验证。S22 已通过隔离 Tk 根窗口、真实控件和合成事件增加控件级集成回归；这不等同于人工桌面验收。S12 仍应在一个无遮挡且输入归属明确的桌面会话中进行一次有记录的最终演示预检：

- 语义实验室：六主题切换；源码只读；正确/错误预测；提交后运行；stdin 和 RuntimeError 输出；重置、键盘操作、关闭。
- 日志工作台/侦探：`WARN + retry + top=2` 查询与同次原始报告；旧结果失效、零匹配、无效文件恢复、Unicode/空格路径；五题结束页、重开、Enter。
- Snake：方向键/WASD、Space、R、失焦暂停、终态重开、窗口缩放。

只操作本阶段启动的目标窗口。窗口被遮挡、出现非本任务输入或事件归属不清时停止输入，不激活/切换其他用户窗口。记录环境、操作、预期、实际和证据类型。无法完成的项保留为“未验证”，并提供答辩现场手动检查清单；不因 S22 自动化测试或最终收尾阶段而虚报 GUI 人工验收通过。

## 三、新克隆、兼容性与 CI

1. 先确认 S12 候选分支包含届时的 `main`，并逐项核对 S23–S31 的主窗口审查记录与实际提交；工作区无用户改动。S23–S30 已在本地 Git 主线不等于逐项验收已完成。
2. 使用独立临时目录创建干净克隆/检出，禁止依赖原工作区未跟踪文件、缓存或本地导入路径。记录准确的 candidate SHA、克隆来源、Python 和操作系统。
3. 在该克隆运行 README 中的实际安装/运行流程、静态检查示例 `python -m lwt --check --format=json examples/modules/main.lwt`、黑盒测试、完整性检查、全量 unittest、compileall、应用 CLI 示例与 LWT 行数工具。静态检查通过不等于程序运行成功，还要执行对应 CLI 示例；对每个命令记录退出码和关键输出。
   同时核对 `python -m lwt.debugger --help` 和脚本化调试示例的 stdout/stderr 分流、退出码及文件路径，确保文档示例可在新克隆复现；调试器测试不替代语言黑盒测试，也不改变正式语言语义。
4. 检查 `.github/workflows/tests.yml` 的当前矩阵。当前仓库配置为 Ubuntu/Windows × Python 3.10/3.13 四格；需要对最终提交逐格核实远端 Actions 结果，不能把本机某一格通过说成 CI 全绿。远端不可用时标记为未验证，并保留 run URL/状态查询结果或精确原因。
5. Python 3.10 官方支持周期已于 2026-10-01 结束；它可以保留为项目声明的最低兼容性测试行，但不要称为当前受支持/推荐的部署版本。优先在当前仍受支持的 Python 版本上完成答辩演示。是否增加较新的 CI 版本，应核对官方版本状态、现有工作流负担和实际可用性后再决定，不得悄悄移除既有 3.10 兼容性目标。依据：[Python Developer’s Guide 版本状态](https://devguide.python.org/versions/)与 [PEP 619](https://peps.python.org/pep-0619/)，查询日期 2026-10-27。

## 四、性能与并发原始证据保护

- 不为“刷新数字”重跑正式性能基准，也不运行会覆盖 `reports/app-concurrency.json` 的并发生成器。
- S28 profile 档案只用于解释器控制流调试与展示，包含额外散列、事件和写盘开销；不得当作 S11 性能对照，也不得与原始性能样本混用。S10 并发证据仍以既有 raw 为准，不因生成 profile 自动刷新。
- 对照最终代码与 raw 中的源文件哈希、运行身份、样本数量、统计值和报告文本；发现不一致时先说明因果及影响，再决定是否需要新 run。旧 raw 不覆盖，任何新数据应追加并保留旧 run。
- PPT 和答辩应说明 S11 测量包含进程启动、导入、词法/语法分析、执行和退出等待；不是纯运行时速度。引用结果时注明操作系统、Python 版本、负载、样本数和限制，不宣称 LWT 更快或把结论泛化到其他平台。
- S10 并发材料说明的是固定只读输入下的多个独立操作系统进程输出一致性，不是 LWT 线程支持，也不证明 GUI 并行性能。

## 五、PPT 内容与制作要求

检查是否已有 PPT；若不存在则创建 `slides/LWT介绍.pptx`。建议 10–14 页，以讲清楚为优先，内容至少包括：

1. 项目目标、作业评分构成和最终交付清单。
2. LWT 语法特色及一个真实可运行的小例子；只称“本项目采用的特色语法组合”，不宣称已证明全球唯一。
3. 解释器流水线：源码 → lexer → parser/AST → runtime → CLI，以及错误位置/退出码处理。
4. 关键语义：作用域/函数、数组和 record、`each` 浅快照、文本内置函数，挑选易答辩内容，不把所有规则挤在一页。
5. 黑盒矩阵覆盖方法、代表性边界错误以及准确的用例数和最后运行 SHA。
6. Agent Skill/指南如何约束 LWT 代码生成，开发记录如何区分 Agent 产出和人工审查。
7. LWT 日志分析器的架构、功能和真实输出；明确它是 246 行有效 LWT，GUI 是调用 LWT CLI 的 Python 展示层。
8. 固定输入多进程读取证据及其边界。
9. LWT/Python 性能方法、实际图表、环境和端到端限制。
10. 预测—运行—解释教学交互，以及 GUI 哪些通过实测、哪些仍未验证。
11. 当前限制、结论和答辩演示顺序。

数字只从最终提交下的报告、命令输出或 raw 重新核对。图表注明单位和样本口径；避免无法读清的小字号、无来源截图和未授权素材。保持中文字体/主题一致，使用可编辑文本和形状。输出 PPTX，并在工具允许时导出/渲染全部页面做视觉检查；修复截字、溢出、字号、对比度及错页后再交付。不能声称未执行的演示或 CI 已成功。

## 六、演示脚本和答辩准备

新增 `docs/demo-script.md`，提供约 5–8 分钟可照读但自然的流程：

1. 用 20–30 秒说明 LWT 目标和语法特色。
2. 跑一个最小 LWT 示例，解释输入、输出与语义。
3. 展示 lexer/parser/runtime 结构或源码入口，讲一条真实边界/错误处理规则。
4. 运行一键黑盒测试并展示覆盖矩阵与真实结果。
5. 运行确定性日志分析示例，展示异常行处理、过滤和统计，强调统计由 LWT 完成。
6. 在桌面安全可用时完成 GUI 预检中最有说明力的一条操作；否则用 CLI 结果演示并明确说明 GUI 人工未验证项，不能播放伪造或未授权录屏。
7. 用一页介绍性能测试方法/结果及限制，再展示 Git/Agent 开发记录。
8. 结尾说明尚未支持的语言特性和可复现限制。

同时准备精简问答卡：为什么不用 Python `eval/exec`、语法如何解析、变量和函数作用域、短路/整数除法/复合值身份语义、错误退出码、黑盒如何覆盖规范、性能计时口径、并发证据能证明什么不能证明什么、Agent 代码如何人工复核、应用为何由 LWT 而非 GUI Python 完成。回答以仓库实现和报告为依据。
