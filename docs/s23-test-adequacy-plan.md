# S23：LWT 黑盒测试强度审计与确定性语义性质验证

状态：**规划完成，待执行窗口实施。** S22 已通过主窗口审查并合入本地 `main`。S23 是用户新增要求的最后一个测试质量阶段；S23 审查通过后直接进入最终 S12，不再增加应用或测试扩展阶段。

## 一、动机与预期收益

课程将解释器实现和自动测试分别计 20 分。项目当前有 194 个逐项黑盒用例、63 条语言规范映射和完整性门禁；这些能说明功能映射与现有样例结果，却不能单独证明测试判定能够识别典型语义回归。

S23 增加两类互补证据：

1. **确定性语义性质测试**：用固定种子生成边界受控的 LWT 程序，按正式规范独立计算预期 stdout/退出结果，再经公开 `python -m lwt` CLI 执行；失败时输出种子、生成源码和复现命令。
2. **小规模人工策划的故障探针**：在临时副本中对解释器注入少数已知语义错误，验证指定现有或新增 `.lwt` 用例能否捕获。只报告每个探针的具体结果，不将有限变异分数表述为总体正确率或真实缺陷保证。

随机/性质测试的设计思路可参考 QuickCheck 原始工作：[Claessen 与 Hughes, “QuickCheck: a lightweight tool for random testing of Haskell programs”](https://doi.org/10.1145/351240.351266)。变异测试研究发现它可以帮助定位测试遗漏，但结果也受到测试集规模、等价变异和项目差异影响；S23 只使用有限、可解释的语义探针，不把单一分数当作质量结论：[Petrovic et al., ICSE 2021](https://research.google/pubs/long-term-effects-of-mutation-testing/)，[Just et al., ICSE/FSE 2018](https://doi.org/10.1145/3180155.3180183)。这些论文提供方法动机，不是本项目的实测证据。

## 二、范围与原则

- 不改语言语义或解释器，除非新用例稳定暴露正式规范偏差；如发现偏差，先报告复现，再由主窗口决定是否拆成语义修复。不得为了提升分数或变异分数改变规范。
- 现有 194 个黑盒用例及已有 expected 结果不得被改写或放宽；新增静态黑盒用例只能覆盖明确、此前未覆盖的规范行为，并同步更新覆盖矩阵和完整性检查。
- 性质生成程序必须输出合法 LWT 源码并通过公开 CLI 测试；新增辅助测试清楚标为补充验证，不计入原有 194 项，除非作为新的 `.lwt`/metadata 成对案例正式纳入并更新矩阵。
- 固定随机种子、固定生成规模、固定 timeout；默认无第三方依赖。每个失败均可一条命令复现。
- 语义预期由规范直接推导，尽量使用独立计算路径；禁止用 Python `eval()`/`exec()` 作为 oracle。
- 故障探针只在 `TemporaryDirectory` 或一次性临时仓库副本操作；每个变异需确认原始代码片段唯一匹配后才应用；绝不修改当前工作树里的正式解释器文件。
- 对等价/未能构造的变异明确标注，不为达到目标比例而保留无效探针。
- 不触碰 S10 并发及 S11 性能数据，不运行相关生成器。

## 三、优先语义范围

先将现有 `docs/language-spec.md` 与 `docs/test-matrix.md` 的高风险边界逐项映射到现有用例，然后选择小而高价值的测试范围。建议覆盖：

- 算术优先级、结合性、负数向下取整除法与余数；
- 严格布尔类型和 `and`/`or` 短路副作用；
- 数组/record 身份相等、别名；
- `each` 进入时浅快照、追加/替换对遍历的影响；
- 函数参数从左到右求值与错误位置/退出码；
- `len`、`split`、`trim`、`to_int` 的 Unicode/边界行为。

不要平均覆盖所有已实现语法；优先挑选“若只改错一个运算符或求值顺序，容易出现静默错误”的规则。报告中说明每项选择为什么对项目风险重要。

## 四、建议实施步骤

### A. 建立测试强度基线

- 读取课程要求、`docs/language-spec.md`、`docs/test-matrix.md`、`project.md` 和现有 runner/用例实现。
- 对每个候选规则列出现有正例、反例、oracle 类型、当前证据与潜在空隙；不要只按文件数量判断覆盖。
- 冻结基线：194/194、当前全量 unittest 数、完整性检查和 LWT 行数；注明 Python/OS。

### B. 实现有界、可重现的性质测试

- 新增标准库工具，例如 `tools/run_semantic_properties.py`，固定 seed（把 seed 写入输出），限制深度和总生成数量，初始目标约 100–200 条受控表达式/程序。
- 通过结构化生成器同时生成 LWT 源码和 oracle 结果；测试算术/比较/布尔表达式时用结构节点随生成同步计算预期值，不能通过解析并执行 LWT 的 Python 模拟器替代真实解释器。
- 可以将多条表达式汇总到少量独立 LWT 文件以控制进程成本；每次仍用公开 `python -m lwt`，精确核对 stdout、stderr、退出码。
- 生成输入限制在正式语法和已定义语义内，避免除零、无限循环、宿主递归崩溃和未定义行为；有意测试错误时明确期望错误类别/退出码/位置。
- 失败输出必须包括 seed、case index、生成源码、期望和实际 bytes 的可读表示以及重跑命令；复现失败后优先把缩减后的确定性最小案例加入正式 `.lwt`/metadata。
- 不宣称固定种子的有限生成等同于形式化证明、穷举或完整覆盖。

### C. 进行有限故障探针审计

- 从当前运行时实际实现里挑选 6–10 个语义明确、可稳定注入的错误版本，例如把向下取整除法改为截断、取消短路、将复合值改为结构相等、将 `each` 快照改为实时遍历、改变参数求值顺序或放宽严格布尔检查。
- 对每个 mutant 记录对应 source patch、目标现有/新增用例、正确版本基线结果和 mutant 结果。
- 使用临时副本中的 `lwt/`、`tools/run_tests.py` 和仅所需 `.lwt`/metadata 成对文件运行公开 CLI。确认子进程实际导入临时 mutant，而非主仓库原模块。
- `mutant killed` 需要有明确失败证据；mutant 存活时判断是测试缺口、等价变异还是注入未生效。注入未生效不计作存活/击杀，必须标为无效探针并修正或剔除。
- 不需要实现通用变异框架，不要对全 runtime 做自动文本替换，不要为单个汇总分数牺牲可读性。

### D. 只补真正发现的覆盖缺口

- 对每个性质失败或存活 mutant 先判断是否违反正式规范、是否已有其他用例已覆盖、是否是等价实现。
- 确有未覆盖的规范条款时，增加最小静态黑盒 `.lwt` 与 metadata；补充 matrix 映射和必要的指南示例。保持原 194 个用例不变，新增用例另计。
- 发现解释器 bug 时，不要在测试阶段无记录地改实现。若确需最小修复，单独提交并同步规范/测试，报告实际影响，主窗口审查时单独看待。
- 不因想达到特定用例数量、mutant kill rate 或宣传效果而添加重复用例。

## 五、验收和交付

- 性质测试在固定 seed 下重复运行两次，输入程序数、结果和摘要一致；至少一条真实 CLI 路径必须验证。
- 每个有效故障探针均要报告 `killed/survived/equivalent/invalid` 和证据；不能只报总分。
- 若新增静态黑盒案例，运行 `python tools/run_tests.py` 并确认新总数、ID 唯一、案例 metadata 配对、matrix 链接完整。
- 运行全量 unittest、项目完整性检查、compileall、LWT 行数统计和 diff check；报告真实输出。
- 新增 `docs/s23-test-adequacy.md`，记录目的、映射方法、生成器 seed/规则、故障探针表、原始/新增用例数、重复性、限制和 S12 交接。
- 更新 `project.md`、README、`docs/test-matrix.md`（若有新静态用例）、阶段路线图、总体/详细规划和 S12 计划。
- 不推送、不合并、不打标签、不开始 S12；在阶段分支提交后保持干净并交主窗口复审。
