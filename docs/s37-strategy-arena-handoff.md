## 1. 目标与评分价值

把单个 LWT Snake 策略扩展成**可替换、可复现、可验证的 LWT 策略实验平台**：在同一 `game.lwt` 规则和现有 LWA1 协议下运行至少两种真正由 LWT 编写的不同决策策略，对固定参数/种子进行有界批量对局，生成每局可由全新 LWT 游戏进程核验的 S35 回放，以及一份可追溯、可离线查看的结果摘要。Python 只选择白名单策略文件、管理独立进程、调用原 bridge、记录原始响应并做统计/呈现；**不计算蛇的方向、碰撞、食物或得分**。

作业第 5 项已有 313 行有效 LWT 游戏和 246 行有效 LWT 日志应用；S36 新增 141 行策略。S37 的价值在于证明 LWT 应用可插拔、能做受控比较、并能由同一语言引擎复算每局，不靠人为演示截图。2–3 分钟答辩可展示“选择两种 LWT 策略 → 固定种子运行 → 结果表 → 打开一局回放 → 故意篡改时验证失败”。不声称新对照策略比 BFS 强，也不将多进程运行称为 LWT 线程能力。

参考依据：[命令重放用于复算而非保存另一套状态](https://gameprogrammingpatterns.com/command.html)、[Python 子进程管道阻塞与退出清理](https://docs.python.org/3/library/subprocess.html#popen-objects)、[median 的统计口径](https://docs.python.org/3/library/statistics.html#statistics.median)。这些文献只提示边界，最终结论以仓库真实测试为准。

## 2. 编码前冻结擂台契约

先写 `docs/s37-arena-contract.md` 并单独提交，包含：

1. **策略清单：** 固定稳定 ID，如 `bfs` 指向 S36 `strategy.lwt`，`baseline` 指向新 LWT 文件 `strategy_baseline.lwt`。用户 CLI 只能选清单 ID，不能将任意绝对路径、网络地址、命令或 Python 脚本当成策略。清单记录源码路径、规范化源字节 SHA-256、LWA1 版本；更换策略内容必须改变 digest。不得改写已有 `strategy.lwt`、`game.lwt` 或 S35 固定回放样例，只为对照新增源文件。
2. **对局输入：** 明确棋盘宽高、有限种子列表、每局最多 TICK 数、每次策略请求/整局 deadline、输出目录、并发度上限。建议默认 8×5、固定 3–5 个 seed、单局至多 100 TICK、并发 1；允许 `--workers 1/2/4` 但有硬上限。参数错误应在创建输出前失败。不要提供无限局数、无限超时或无限文件增长。
3. **对局算法：** 每个 `(策略 ID, seed)` 新开独立长驻游戏与策略进程；向游戏 INIT/START，循环 `已验证快照 → LWT 策略建议 → 必要 TURN → TICK`，到 WON、GAME_OVER、NONE/TRAPPED、上限或故障停止。任何真实游戏命令只经现有 `LwtSnakeBridge`/recorder，所有分数/阶段从真实快照获取。`NONE` 不是胜利；策略失败是失败记录，不被记为普通得分 0。每局退出时 QUIT/EOF、排空与回收两子进程。
4. **回放与数据：** 对局记录使用 S35 现有 JSON 格式与 `save`、`reconstruct`，不发明第二份坐标真值。每局 JSON 结果必须含 schema 版本、策略 ID/digest、game digest、board、seed、tick 数、真实终局/停止原因、分数、回放相对路径与 SHA-256、是否经新进程验证、错误类别（若有）。写入新输出目录且默认拒绝覆盖非空目录；原子写结果、失败也保留已完整录制的前缀和明确失败原因。路径必须可移植，输入/结果大小有界。不要覆盖 S10/S11/S28/S29/S34/S35/S36 原始证据。
5. **统计解释：** 每个策略使用同一组 seed 和棋盘配置；按 `(策略 ID, seed)` 固定顺序输出，不受 worker 完成顺序影响。报告完成/失败数、终局类别、每局分数与 TICK 数、分数 median/min/max；不能把不同种子、失败局或未完成局悄悄混成一个“胜率”。同 seed 只控制初始 PRNG，策略走法不同会改变吃食物时机与随后食物位置，故不是全程相同食物序列，不能作严格因果优劣断言。计时如有，标注端到端范围，不混入 S11。

## 3. 两种 LWT 策略与核心运行器

- 新对照策略必须是独立真实 LWT 源程序，遵守 S36 LWA1 请求/响应、序号、ASCII、EOF、错误边界。建议最小但有可解释算法差异：在合法一步中优先维持当前方向，否则按 U/R/D/L 选首个合法方向；它只检查本步，不做 BFS。所有方向合法性也由 LWT 源码执行，Python 不代算。`baseline` 的目的仅是可比较、可教学，不用刻意造弱策略或保证特定输赢。
- 运行器建议 `python -m app.lwt_snake.arena --seeds 4,7,11 --max-ticks 100 --workers 1 --output <new-dir>`。另提供 `--verify <result.json>` 对每局回放重新开启新 LWT 游戏进程并逐笔核对，核对 source/replay digest 与元数据的一致性；不允许运行结果 JSON 自述“verified=true”代替验证。汇总命令可在无 Tk 环境运行。
- 对 `--workers 2/4`，每个 worker 仅持有自己的一对 LWT 子进程和 recorder，不共享进程 stdin、序号、可变快照或文件名。收集完成后按固定键排序，生成**去除 PID/耗时后的相同逻辑结果**。取消/超时应停止新任务、终止当前子进程、保留完整前缀和清楚的错误，不能留下后台进程。队列和活跃进程数有界。
- 可提供轻量图形结果入口（Tk 表格或本地静态 HTML），但它必须读取已校验的结果文件，展示策略、seed、分数、TICK、终止原因和“打开/验证这局回放”。不得为了图表在 Python 重新模拟游戏；若 GUI 实现显著影响稳定性，先交付完整 CLI + 可读 Markdown/HTML 报表，再将 GUI 作为有明确验收的次级增强。不要把额外 UI 作为隐含通过条件。

## 4. 测试与审查门槛

测试应能抓住行为偏差，而非逐行镜像实现：

1. **策略协议：** 新 baseline 在真实 `python -u -m lwt` 中对合法/非法帧、序号、待执行 TURN、尾格、墙/身体、完全无合法方向、EOF 给出确定结果；同输入连续两次响应可复现。S36 BFS 固定用例仍全过。
2. **对局真实性：** 真实两个 LWT 策略 × 至少三个固定 seed；每局录制的 TICK、TURN、最终快照与结果元数据逐项一致；退出旧进程后 `--verify` 通过。人工改一笔 score、改 seed、换策略 digest、缺回放、改 game digest，应非零退出并指明哪局/哪笔/哪个字段，不把坏文件纳入统计。
3. **并发与故障：** 同一配置在 workers=1/2/4 输出的去时序逻辑结果一致，文件互不覆盖，最终活跃子进程为 0。注入策略超时、坏帧、非零退出、stderr 洪流、游戏异常、取消、写文件失败，确保不死锁、不伪造成功、不遗失已完整前缀；对失败局统计和退出码有冻结契约。不要用工作机瞬时耗时的固定阈值来判逻辑正确。
4. **遗留回归：** S35 父子回放和分歧示例、S36 真实 CLI/GUI 23 项、S10 原应用 25 项、语言黑盒 287 项、完整性、全量 unittest、compileall、静态检查两个 LWT 策略、两个原课程应用行数、相对链接/围栏、`git diff --check`。严格 GUI runner 若实际运行必须 `skip=0` 才算 GUI 自动通过；人工物理键鼠/视觉仍单列未验证。
5. **性能/可用性：** 选择小规模固定运行确保答辩 2–3 分钟内能展示；大棋盘 BFS 已在 S36 约 0.14 秒暖查询，赛事总时长可能大幅增长。记录实际总时长和每局长尾，必要时降低默认 tick/seed 数，不能删安全上限或将快慢误写成语言性能胜负。
