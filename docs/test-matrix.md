## 2. 用例格式、发现和比较规则

### 2.1 JSON 元数据格式

每个普通语义用例有一对同名文件，例如 [`input-lf-and-crlf.lwt`](../tests/cases/builtins-text-io/input-lf-and-crlf.lwt) 和 [`input-lf-and-crlf.json`](../tests/cases/builtins-text-io/input-lf-and-crlf.json)。以下是完整、可运行的 metadata 示例：

```json
{
  "id": "one-line-input",
  "spec_refs": ["6"],
  "tags": ["normal"],
  "args": [],
  "stdin": {"text": "hello\n"},
  "timeout_seconds": 5,
  "expected": {
    "exit_code": 0,
    "stdout": "hello\n",
    "stderr": ""
  }
}
```

字段规则：

- `id`：全库唯一的 ASCII 小写短横线标识符，模式为 `[a-z0-9]+(?:-[a-z0-9]+)*`。
- `spec_refs`：非空且不重复的规范章节编号数组，例如 `2.1`、`4.3`、`9`；值只能引用规范 §1–§9。
- `tags`：可选的字符串数组，缺省为空数组；标签不重复。
- `args`：字符串数组，作为 LWT 程序参数，缺省不允许省略（空数组表示无参数）。空字符串、空格、Unicode 和字面量 `--` 均保留。
- `stdin`：必须恰有一个键。`{"text":"..."}` 将 JSON 字符串以 UTF-8 编码；`{"base64":"..."}` 使用严格 Base64 解码，适合非法 UTF-8 等任意字节输入。
- `expected`：字段必须且仅能是 `exit_code`（0–255 的整数）、`stdout` 与 `stderr`（UTF-8 字符串）。三者逐字节比较；JSON 换行转义会解码为实际 LF。
- `timeout_seconds`：可选有限正数，缺省 5 秒；最大 30 秒。布尔值、零、负数、NaN/Infinity 和超上限值均为配置错误。
- `cli_args_override`：可选字符串数组，表示 `python -m lwt` 后面的完整 argv，仅供 CLI 契约测试。设置后 `args` 必须为空；同名 `.lwt` 仍配对，但不会执行，矩阵中此类用例只算 CLI 覆盖、不算程序语义覆盖。
- 所有对象均严格校验：缺失/未知字段、类型不符、重复 JSON 键、无效 JSON/Base64、重复 ID 或无效超时都会使整次运行以非零码失败，且不运行部分用例。

### 2.2 发现与运行

runner 以自身文件定位仓库根目录；递归发现顺序按 POSIX 相对路径排序。名为 `fixtures` 的目录在任意测试类别内均不参与用例发现；其余每个 `.lwt` 必须恰有一个同路径 `.json`，反之亦然。类别目录中的其他文件、符号链接、孤立文件、空用例集和配置错误均使整次执行失败。

普通语义用例执行的进程参数为 `[sys.executable, "-m", "lwt", <仓库相对 POSIX 源路径>]`；只有 `args` 非空时才追加 `--` 与参数列表。`cwd` 固定为仓库根目录，stdin 直接传字节，stdout/stderr 捕获为字节，`shell=False`，每项有有限超时。CLI override 用其提供的完整参数数组替换源路径构造，只覆盖 CLI 行为。

stdout、stderr 和退出码都精确比较。跨平台时只将 `CRLF` 规范为 `LF`；孤立 CR、空白、尾随换行、诊断正文和输出顺序均不忽略。失败会列出稳定 ID、失败类别、expected/actual 字节表示及文本 unified diff；超时显示期望结果和已经捕获的部分输出。所有用例运行完后汇总通过/失败/总数、类别计数和耗时。配置错误则不执行任何案例并退出非零。

## 3. 逐条规范规则覆盖矩阵
