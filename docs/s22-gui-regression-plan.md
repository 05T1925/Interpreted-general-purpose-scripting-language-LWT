# S22：Tk 图形界面交互回归与交付前可靠性提升

状态：**规划完成，待工作执行窗口实施；S12 仍是最终交付阶段。** S22 是 S21 与 S12 之间最后一个质量阶段，目标是用真实 Tk 控件和可重复事件测试补足现有应用的交互回归证据；它不增加新的产品功能，不取代 S12 的桌面人工演示预检。

## 一、为什么值得单独做这一阶段

S21 已诚实记录：语义实验室、日志工作台/五题挑战和贪吃蛇的实际桌面交互均因目标窗口遮挡而未验证。项目已有无头核心测试、CLI 集成测试和代码审阅，但这些不能证明 Tk 控件绑定、窗口事件、异步结果回填和销毁时回调清理按预期协作。

S22 的创新重点是把 GUI 验收从依赖某一时刻可用的人工桌面，提升为可在隔离 Tk 根窗口内重复执行的控件级集成回归。使用真实 Tk/Ttk 控件、真实窗口层级和真实事件循环，通过 `.invoke()`、`event_generate()`、受控队列和确定性测试夹具验证交互契约。需要外部 CLI 时保留至少一条真实子进程路径；只在超时、启动失败等难以稳定触发的边界替换进程适配器。

这类合成事件只能证明被测 Tk 控件和程序回调的集成行为，不能证明物理键盘/鼠标、输入法、窗口管理器、桌面可视效果、可访问性或真实用户体验。S12 仍须执行可归因的现场检查；若现场桌面不可用，必须保留未验证项。

## 三、测试设计原则

1. 先检查 Python/Tk/Tcl 版本和显示环境，再选择可运行方式。测试必须使用真实 Tk/Ttk 控件和实际应用窗口类；仅 mock 整个 `Tk`、窗口或被测控件不算 GUI 集成测试。
2. 使用隔离的测试根窗口；能在不显示或虚拟显示服务下验证的就不占用用户桌面，不移动鼠标、不向其他窗口发键盘事件、不激活/切换用户窗口。
3. 对按钮优先调用实际控件 `.invoke()`；对绑定键盘和窗口事件使用 `event_generate()` 并正确设置焦点、运行 Tk 事件队列。记录事件是否因焦点或平台限制而不能合成，不绕过应用事件绑定直接调用内部方法后宣称控件测试通过。
4. 有异步 worker 的测试使用明确的 `threading.Event`、队列或可控完成信号推进状态；使用有上限的事件循环轮询，不用长时间 `sleep()` 作为同步手段。确认 worker 不直接操作 Tk 控件，关闭后迟到结果不会访问已销毁窗口或覆盖新状态。
5. 默认保持标准库方案。若 Linux runner 没有显示服务，先核验 `xvfb-run` 是否已提供；确有必要才在 CI 中加入范围最小、可解释的虚拟显示步骤。不得把“测试因无显示而跳过”记为通过；CI 应显示 GUI 集成用例的实际运行数与跳过数。
6. 可以在异常边界使用 `unittest.mock`，但应 patch 被测模块实际查找依赖的命名空间，并使用 `spec`/`autospec` 限制接口；核心状态转移、widget 绑定、报告解析与成功 CLI 流程不能全部被 mock 掉。
7. 每条结果分开标注：无头核心测试、真实 Tk 控件/事件集成测试、真实 LWT 子进程集成测试、可归因人工桌面操作、静态审阅。不同证据不能互相代替。

## 四、必须覆盖的交互场景

执行窗口先读 S21 报告和三个 GUI 的实现/测试，按现有控件和可注入边界细化测试。至少覆盖下列场景；若控件/测试名称不同，在报告中记录实际映射。

### A. LWT 语义实验室

- 用真实控件选择六个固定主题，确认选中主题、源码和预测题同步变化，源码区域保持只读。
- 在未提交预测前尝试运行，确认 Run 控件状态和事件行为遵守“先预测再运行”；提交预测后真实运行固定白名单示例，核验预测反馈与 CLI 输出/退出码分别显示。
- 覆盖成功 stdout、stdin 示例、预期 RuntimeError 示例；确认错误示例仍显示真实 stderr/退出码与解释，不伪装成普通成功。
- 在运行、切换题目、重置及关闭窗口之间推进异步结果；旧 revision 结果不得覆盖当前题目，窗口销毁后回调不得操作已销毁控件。
- 验证按钮和可合成键盘事件的绑定。键盘焦点/输入法/OS 级快捷键无法可靠合成的部分单列，不夸大覆盖。

### B. 日志分析工作台与五题挑战

- 通过真实控件填写或选择演示路径、Level/Keyword/Top，触发真实 `python -m lwt` 子进程；断言界面所示条件、argv、摘要和本次完整原始报告属于同一请求。
- 覆盖默认查询、`WARN + retry + top=2`、零匹配、非法/缺失文件错误，以及错误后的恢复重试。
- 在请求执行中更改条件、快速连续请求或关闭窗口，确认旧结果不能覆盖新条件；查询按钮忙闲状态和队列回填由真实 UI 生命周期更新。
- 通过真实挑战控件完成至少一轮从第一题至第五题的状态推进，验证正确/错误反馈、分数/进度、最终页、重新开始及 Enter 绑定。
- 对异常/超时测试可注入受控 runner；至少保留一个成功案例真实启动 LWT 子进程，防止测试只验证 mock 编排。

### C. 贪吃蛇

- 通过实际开始按钮和可合成方向键/WASD 事件驱动游戏；确认运行状态、方向规则和 Canvas 重绘与核心状态一致。
- 覆盖 Space 暂停/继续、R 重置、方向键在按钮焦点情形、窗口 FocusOut/FocusIn 事件处理、撞墙终态和终态主按钮重开。
- 使用受控定时器/`after` 回调推进固定 tick，验证同一时刻不重复安排 tick；暂停、失焦、重置和关闭后旧 tick 不再推进状态。
- 至少选择一个窄尺寸和一个较大尺寸，检查实际 Tk 几何请求/画布布局没有负尺寸、越界或关键控件消失。几何断言只称布局约束测试，不称人工视觉审美验收。

## 五、显示环境与 CI 决策

- 优先使用仓库当前 `.github/workflows/tests.yml` 的 Linux/Windows 与 Python 矩阵，先探测真实运行效果，再决定 GUI 集成测试在哪些格执行。
- Linux 无 `$DISPLAY` 时可用 Xvfb 为 Tk 提供隔离显示；不得通过桌面自动化向真实用户会话发送按键来跑 CI。
- 如果 Windows CI runner 无法可靠启动 Tk 根窗口，不要让所有测试因它失败或被静默跳过；将 GUI 集成测试放在有可靠显示服务的 Linux CI 格，并把其余平台列为未验证。除非确有必要，不扩大现有 Python/OS 矩阵。
- CI 日志应清楚区分 GUI 集成用例的 run/pass/fail/skip 数，以及虚拟显示服务启动是否成功。测试因环境缺失跳过时，步骤不得输出“GUI 全通过”。
- 不以窗口标题/句柄、`Tk()` 成功、`compileall`、源码审阅、模拟方法调用或已有 core 单测作为真实 GUI 交互通过证据。

## 六、实现建议与质量门槛

- 优先依赖已有 UI/core 分层，为测试添加最小的构造参数或 runner/timer 注入点；避免为测试建立复杂通用 GUI 框架。
- 直接操控用户桌面不属于自动化方案。测试可用 Tk 的控件命令和合成事件，但必须断言可见控件状态、按钮启用状态、文本内容、Canvas/页面状态和真实子进程结果。
- 测试必须可重复、有限时、独立清理 root/临时文件/子进程/after 回调，不能留下后台窗口或线程。
- 若要接入 CI，更新 workflow 并在本机模拟相同命令。平台依赖采用最小安装步骤，并记录来源、失败处理和没有显示服务时的状态。
- 若复现缺陷，先给出重现步骤和失败测试，再做小修复，加入失败前后回归证据；不得只调整断言让测试通过。
- 完成后运行全量 unittest、LWT 黑盒 `python tools/run_tests.py`、`python tools/check_project_integrity.py`、`python -m compileall -q lwt tests tools bench app`、LWT 行数统计和 `git diff --check`。若改 workflow，核对 YAML 结构、矩阵行为和条件步骤。
- 对六个 S10/S11 保护文件及 `lwt/`、正式规范、黑盒矩阵与 S10 CLI 契约，逐项相对阶段基线核验。任何预期变更须解释；并发/性能 raw 必须保持不变。

## 九、参考依据

- Python 官方 Python 3.10 Tkinter 文档指出 Tkinter 是 Tcl/Tk 事件驱动接口，界面依赖 event loop；事件处理器应保持快速，长任务应拆分或放到其他线程。该依据支持对工作线程与主线程 UI 生命周期设计做集成验证，不是本项目自身通过测试的证据：[Python 3.10 Tkinter — Threading model](https://docs.python.org/3.10/library/tkinter.html#threading-model)。
- Tcl/Tk 官方事件手册说明可以合成窗口事件，但某些键盘事件需要焦点。因此 S22 的 `event_generate()` 用例应明确视为控件/绑定集成测试，而不是物理设备或人工可用性测试：[Tcl/Tk event manual](https://www.tcl-lang.org/man/tcl8.6/TkCmd/event.htm)。
- Python 官方 `unittest.mock` 文档说明 mock/patch 用于替换被测依赖并检查交互；S22 仅在外部错误边界使用 mock，保留实际 Tk 控件与至少一个真实 CLI 成功路径：[unittest.mock](https://docs.python.org/3/library/unittest.mock.html)。
