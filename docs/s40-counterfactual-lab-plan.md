# S40 派发规划：可验证的 LWT 策略反事实实验台

状态：**仅规划，尚未实施**。S39 已通过[主窗口复核](s39-main-review.md)，本地 `main` 已快进到审查修正提交；执行窗口开工前仍须重查本地与远端真实状态。本阶段完成并复核后再执行 [S12 最终交付](s12-final-delivery-plan.md)。

## 为什么做这一项

[课程原文](../大作业内容.md)中 Agent 编写 LWT 应用及其可展示的完整性占 30 分。S34–S39 已有 LWT 游戏、三份 LWT 策略、长期进程、回放与双层验真；但目前若要解释“同一局面下不同策略为何选择不同方向，以及替代一步会怎样”，需要分别阅读多个 JSON 和命令行输出。S40 将这一问题收束为**同一已验证观察轨迹上的多策略咨询、只推进一步的替代分支和可重验的交互展示**。它不声称能预言替代策略的整局成绩。

设计借鉴 Robocode 的“编码策略—运行对局—记录—可视复盘”闭环：[Robocode 官方说明](https://robocode.sourceforge.io/docs/ReadMe.html)与 [Tank Royale 官方 GUI 组件说明](https://github.com/robocode-dev/tank-royale/blob/main/docs/architecture/c4-views/gui-components.md)。这只是工作流借鉴，不引入对方实现或素材。Tk 的事件循环和线程边界参考 [Python 官方文档](https://docs.python.org/3/library/tkinter.html)。

## 必须先冻结的含义

1. 只接受 S39 v3 且选中对局 `game_verified=true`、`policy_verified=true`、`stop_reason` 非失败的证据。调用现有 `arena.verify(..., catalog_path=...)` 做完整双层验真；自定义策略仍要求用户**显式提供**可信本地 catalog。不能从结果文件中的路径自动执行源码。v1/v2 输入本阶段可明确拒绝，不声称兼容。
2. 以选中对局的第 N 次 LWA1 咨询为锚点；N 为一基整数且不能超过决策数。用 S35 的 `reconstruct` 在新游戏进程中重建咨询前状态，严格对应 `game_transaction`，不从结果 JSON 自称的分数、蛇身或方向构造状态。
3. 每个候选策略使用**自己的新长驻 LWT 策略进程**，按顺序接收原对局从第 1 次到第 N 次的相同已验证状态序列，以保持协议序号和可能的策略内部状态。到 N 时比较 `MOVE` 方向与 `FOOD/SPACE/TRAPPED` 原因。这个结果叫“同一观察轨迹上的策略响应”，不能说是“其他策略原本自然对局第 N 步的响应”。
4. 对允许的候选 `MOVE`，从锚点前缀**另启新 LWT 游戏进程**，按建议发送必要 `TURN` 和恰好一个 `TICK`；保存完整带来源的分支回放，再用另一全新游戏进程复核事务、最终局面与分数。`NONE/TRAPPED` 不强制推进。仅展示这一步的即时变化，不把一时得分推断成整局优劣。
5. 比较结果与新回放需绑定原 v3 result 原始字节摘要、catalog/策略源码摘要、选中 `case/step`、实际咨询前事务索引、候选 LWA1 帧、分支回放路径与 SHA-256。所有 `verified` 标志在加载时重算，不信任 JSON 的自述。定义严格、版本化、大小与数目有界的格式；拒绝重复键、路径穿越、软链接、摘要不符、未知字段、错误类型及不兼容版本。文件写入使用临时文件加原子替换，不覆盖已有输出目录。

## 功能范围与交互

- 新增 `python -m app.lwt_snake.counterfactual` CLI，至少支持 `--analyze RESULT --catalog FILE --case ID/SEED --step N --strategies ... --output NEW_DIR`、`--verify DIR`（v3 仍要显式 catalog）和面向答辩的逐步文本解释。实际参数可在契约冻结时微调，但须保持一条可复制的无 GUI 演示命令。目录中的内置/自定义 ID 只能来自 S39 已验证的映射；输入规模、总截止时间及每进程超时沿用或严于 S39。
- 增加独立 Tk 图形实验台入口，例如 `python -m app.lwt_snake.counterfactual_ui`：选择固定演示或受控目录结果、对局、步数和候选策略；后台执行验真与计算，主线程通过队列更新控件；显示原局面、每个候选的响应/原因、一步后局面/分数变化、游戏证明与策略证明状态，并可前后切换步骤。必须明确标出“共享观察轨迹”和“一步分支”，并能查看原始证据/运行命令。
- GUI 可以重用现有 Snake Canvas 绘制与主题，但不要复制游戏规则。关闭、取消、切换选择、超时和失败后不能留下游戏/策略子进程或让旧结果覆盖当前选择；GUI 缺 Tk 时给可读非零诊断。真实人工桌面操作的结果应与自动 Tk 测试分列。
- 提供一个真实、有**方向分歧**的固定演示锚点。先从 S39 九局中按同局面轨迹实测寻找；若没有，使用受控固定种子/步数生成新的 v3 小局，并保留检索过程。不得伪造决策或用两个不同游戏局面冒充同局面。固定示例至少含原结果、候选响应、两条可复验的一步分支和一条故意篡改的失败样例。若某策略返回 TRAPPED，应如实显示并给出其他可比较的 MOVE 案例。

## 代码边界与风险控制

- LWT 游戏规则、策略选择、碰撞、食物和分数仍由真实 `python -m lwt` 子进程计算；Python 负责协议、证据、进程生命周期、界面和统计显示。不得在 Python 复制游戏规则，不通过 Python `eval`/`exec` 执行 LWT 源码。
- 不修改解释器语义、正式规范、287 组黑盒、S10 日志应用/并发原始数据、S11 性能原始数据、S28/S29 证据、S35/S37/S38/S39 固定结果或现有策略源码，除非先找到可复现阻断缺陷并单独提交修复与回归。新实验数据存放独立 `reports/s40-*`。
- 自定义 LWT 策略是可信本地可执行源码。延续 S39 的显式目录和摘要绑定；不要把目录/超时写成对陌生策略的沙箱。
- 分层提交：先冻结协议/文件契约，再做 CLI 与无头测试，再做 Tk 与控件测试，再做确定性演示与文档。不要为本阶段增加新的语言特性、第三方 GUI 依赖、在线服务或 Marketplace 发布。

## 验收门槛

1. 实际运行固定演示的分析、全新进程验真和逐步解释，记录完整命令、退出码、候选方向/原因、原/分支即时分数；相同输入重复生成核心逻辑 JSON 字节一致。篡改原结果、策略/目录摘要、候选帧、分支事务、case/step、路径和“已验证”标志时，验真必须非零且指出具体证据层。
2. 子进程故障、非法 UTF-8/JSON、启动失败、超时、取消、GUI 快速切换/关闭都要有有限、必要的回归测试。测试结束检查无残留 LWT 游戏/策略进程。
3. 运行本阶段定向 CLI/GUI 测试、`python tools/run_gui_integration.py --require-no-skips`、全量 unittest、`python tools/run_tests.py`、`python tools/check_project_integrity.py`、三份 LWT 策略静态检查、`compileall`、`git diff --check` 与文档相对链接检查。记录每条实际结果；不可把旧 509/287/23 基数自动当成新结果。
4. 文档写清模型、可复现命令、三类证据：执行窗口实际测试、主窗口/远端 CI 待审、人工物理键鼠仍待 S12。答辩 2–3 分钟路径应能从 Agent 的 LWT 源码跳到相同局面决策、分支和验真，再回到课程交付映射。
5. 在独立 `feature/lwt-counterfactual-lab` 分支提交，报告基线、完整提交 SHA、变更文件、验证、失败修复和剩余风险。执行窗口不合并、不推送，不开始 S12；交由主窗口审查。

## 缩减顺序

若时间或可靠性与范围冲突，优先保留**CLI 的真实同局面咨询、单步新进程分支、严格验真与确定性证据**；GUI 先完成固定演示的只读可交互步进，再考虑新结果生成。不得牺牲证据正确性换取多张图或复杂动画。通过本阶段后应收束功能开发，进入 S12。
