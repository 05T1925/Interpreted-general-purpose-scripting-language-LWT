## 二、为什么做这个功能

作业第 5 项要求 Agent 使用 LWT 编写不少于 200 行且功能完整的应用；现有 `game.lwt` 已为 313 行有效 LWT，日志应用为 246 行。S36 的增量让 LWT 再承担有实际算法复杂度的寻路决策，答辩可以现场展示“LWT 规则引擎 + LWT 策略进程 + Python 可视化/协议桥接 + S35 可验证回放”的端到端数据流。宽度优先选择已存在的语言能力（数组、循环、函数、模块、`break/continue` 等），不要为此追加 LWT 语言语法或 Python 游戏规则副本。

设计依据：无权图的 BFS 可求静态网格中的最短步数；蛇身随时间移动，所以静态 BFS 只是本步启发式，不是全局正确性证明。[BFS 原理](https://cp-algorithms.com/graph/breadth-first-search.html)。游戏循环需要把输入、状态推进与绘制的时序说明清楚，[Game Loop](https://gameprogrammingpatterns.com/game-loop.html)。Tk 事件回调应迅速返回，长计算放在线程/子进程，并由 Tk 所属线程更新控件，[Tkinter threading model](https://docs.python.org/3/library/tkinter.html#threading-model)。长驻子进程需要同时排空 stdout/stderr、设置上限和超时，避免 PIPE 阻塞，[Python subprocess](https://docs.python.org/3/library/subprocess.html#popen-objects)。这些文献用于确定工程约束，不替代本仓库实测。

## 三、先做的核对与协议冻结

1. 复查 S35 `GameSnapshot` 中 `direction` 的含义：它是下一次移动方向，可能包含尚未消费的 TURN。确认现有回放/接管的序号、generation、clock 和 worker owner。先写一页短设计/协议文档，单独提交，再编码。
2. 新策略使用**独立的长驻公开 LWT CLI 子进程**，建议入口 `python -u -m lwt app/lwt_snake/strategy.lwt`。不可 `eval/exec` LWT，不能把策略移植到 Python。独立进程使现有 `game.lwt` 字节和 S35 回放源码摘要保持不变。明确策略与游戏进程的 PID、stdin/stdout/stderr、关闭顺序和失败隔离。
3. 冻结一个仅含 ASCII 的逐行协议，例如请求 `LWA1|SSSSSS|WIDTH|HEIGHT|DIR|FOOD_X|FOOD_Y|BODY_LEN|x,y;x,y;...`，响应 `LWA1|SSSSSS|MOVE|U/R/D/L|FOOD/SPACE` 或 `LWA1|SSSSSS|NONE|-|TRAPPED`。`SSSSSS` 从 000001 单调递增，宽高与现有引擎相同，body 头到尾；只对 RUNNING 状态查询，食物不能为空。允许实现者在编码前调整字段，但**必须先冻结精确数量、顺序、合法值、长度上限、错误帧、EOF 与退出行为**，测试/文档/实现同步。协议不得直接信任回放文件或 GUI 文本作为指令。
4. Python 侧只把经现有 bridge 校验的快照编码为策略请求；它可以验证策略返回的版本、序号、方向、帧长、ASCII 和是否是当前快照的结果，但不计算 BFS 或选择方向。若返回的 MOVE 对当前快照显然非法，可拒绝并停止自动驾驶，而不是悄悄改为 Python 方向。保持 `shell=False` 和 argv 数组。明确子进程超时、stderr 限额、额外 stdout、EOF、半帧、错序、退出非零、队列满、关闭后的旧结果、用户取消等边界。

## 四、LWT 策略的可复现语义

在 `app/lwt_snake/strategy.lwt` 中编写纯 LWT 决策代码，并用注释说明算法步骤。建议固定方向优先序 `U,R,D,L`，使同一快照得到同一响应。

1. 从协议帧严格解析棋盘、食物、当前/待执行方向和蛇身。输入必须是经约束的十进制 ASCII；非法字段返回协议错误或清楚的非零诊断，不能输出伪合法 MOVE。EOF 安静退出。
2. 列出四个候选下一步：排除直接逆向、墙外、身体碰撞；普通移动允许进入本步离开的尾格，吃食物时尾格不离开。以现有 `game.lwt` 规则为判定基准，尤其要测试“已排队 TURN”“尾格可进入”“吃食物尾格不可进入”。
3. 对每个候选预测**本步后的身体占用**，在该静态网格上用队列式 BFS 计算新头到食物的距离和可到达空格数量。禁止用 Python 计算路径。优先选能到食物、且可达空间足以容纳当前蛇身（或本步直接吃到食物）的候选；在这些候选中选距离最小者，同距离按固定方向序。没有合格食物路线时选可达空格最多的合法一步，平局仍按固定序；完全无合法一步时输出 `NONE`。若实际实现采用更保守的规则，先在协议文档写清并给出反例测试。
4. 这是单步静态预测。未来身体会移动、食物会重新生成，因此测试只保证“返回方向符合这一步的游戏约束、选择结果确定、后续真实引擎事务能验证”。不得声称 BFS 一定吃到食物或一定不会在后续困死。
5. 策略程序应在 24×18 棋盘、最大 432 格的协议边界内结束。用有限数组和显式上界控制内存/时间；测量常见与最大棋盘的真实 LWT 响应延迟，若过慢应简化策略或调整自动驾驶节拍，不通过降低安全校验换取表面流畅。

## 五、应用接入与用户体验

1. 在现有 LWT Snake 窗口中加入清晰区分的“提示”和“自动驾驶 开/关”控件，显示策略方向、`FOOD/SPACE/TRAPPED` 理由及“策略由 LWT 计算”。提示箭头不能遮挡食物/蛇头；提示未返回时显示计算中，出错时显示可读原因。关闭提示或快照改变后，旧结果不得覆盖新状态。
2. 手动模式保留 S35 `GameClock` 行为。自动模式使用**单一串行决策链**：当前快照 → 策略响应 → 可选 TURN → TICK → 新快照，下一链仅在上一链完成后开始。不要让手动时钟与自动链同时发 TICK；慢响应不补发积压 TICK。确保切换模式不会继承过期 deadline 或重复推进。
3. 用户主动方向键/按钮转向时，明确约定为退出自动驾驶并由用户接管；提示查询不修改游戏，故不应出现在 S35 事务回放中。自动驾驶真正执行的 TURN/TICK 必须通过现有 worker/bridge，进入 recorder；不能直接改 `GameSnapshot`、snake、food 或 score。
4. PAUSE、RESET、GAME_OVER、WON、失焦、回放载入、复盘、接管、保存对话框、窗口关闭都要定义自动策略/提示的取消和恢复规则。特别是 S35 验证/接管期间不能保留旧策略进程结果；新一代 generation/request ID 必须使旧响应失效。自动模式在失焦时暂停，不应在窗口重新获焦后自行续跑。
5. 策略异常/超时/协议错误时：停止自动驾驶、停止自动 TICK、保留最近已由游戏进程确认的快照与 S35 完整事务前缀，提示用户可转回手动；不得伪造策略建议或 silently fallback 到 Python 策略。用户可安全重试启动新策略进程。所有 Tk 控件更新在创建 Tk 的主线程；后台工作线程不触碰 widget。
6. 不覆盖已有 `app/log_report.lwt`、S10/S11 raw、S28 profile、S29 smoke、S34 roundtrip、S35 固定回放 JSON。尤其**不要修改 `app/lwt_snake/game.lwt`**，否则旧 replay 的 source digest 将失效。如发现必须修游戏规则的独立缺陷，先提供最小复现与影响分析，独立提交修复，并把旧回放兼容性问题交主窗口裁定，不直接重写证据。
